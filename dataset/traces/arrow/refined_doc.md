# arrow Baseline Documentation

## Module: util

**Purpose**: Provides small internal validation and conversion helpers for Arrow’s date/time handling, including weekday calculation, timestamp normalization, ordinal validation, ISO-week conversion, and interval-bound validation.

**Functions**
- **next_weekday(start_date, weekday)**: Returns the first occurrence of a given weekday (0=Monday..6=Sunday) on or after `start_date`, using `dateutil.rrule` with a weekly recurrence.
- **is_timestamp(value)**: Determines whether `value` can represent a numeric timestamp by rejecting booleans and non-numeric types, then attempting `float(value)`.
- **validate_ordinal(value)**: Ensures `value` is a non-boolean `int` within `[MIN_ORDINAL, MAX_ORDINAL]`, raising `TypeError` or `ValueError` otherwise.
- **normalize_timestamp(timestamp)**: Converts millisecond or microsecond epoch values down to seconds when `timestamp` exceeds `MAX_TIMESTAMP`, using `MAX_TIMESTAMP_MS`/`MAX_TIMESTAMP_US` thresholds and rejecting overly large values.
- **iso_to_gregorian(iso_year, iso_week, iso_day)**: Converts an ISO week date (week 1–53, day 1–7) into a `datetime.date` by anchoring on Jan 4 and computing the corresponding Gregorian date.
- **validate_bounds(bounds)**: Validates that an interval bounds string is one of `"()"`, `"(]"`, `"[)"`, or `"[]"`, raising `ValueError` otherwise.

**Relationships / external types**: These helpers operate on standard `datetime.date`/`datetime.datetime` and Arrow’s range constants from `arrow.constants`, with `next_weekday` relying on `dateutil.rrule` for recurrence calculation.

## Function: next_weekday

```python
def next_weekday(start_date: Optional[datetime.date], weekday: int) -> datetime.datetime
```

**next_weekday**: Compute the first occurrence of a given weekday on or after a start date using a weekly recurrence rule.
**Signature**: def next_weekday(start_date: Optional[datetime.date], weekday: int) -> datetime.datetime
**Parameters**:
- start_date (Optional[datetime.date]): Start date/time used as the recurrence start (`dtstart`) for the search; may be `None` (passed through to the underlying recurrence rule).
- weekday (int): Target weekday as an integer where 0=Monday and 6=Sunday; must be within 0..6 inclusive.
**Behavior**:
- Validate `weekday`:
- If `weekday` is less than 0 or greater than 6, raise `ValueError` with the message "Weekday must be between 0 (Monday) and 6 (Sunday).".
- Create a `dateutil.rrule.rrule` recurrence with:
- `freq=WEEKLY`
- `dtstart=start_date`
- `byweekday=weekday`
- `count=1`
- Index the first (and only) generated occurrence from the recurrence (`[0]`) and return it.
- The returned occurrence is the first matching weekday that is on or after `start_date` according to the recurrence rule.
**Returns**:
- A `datetime.datetime` representing the first occurrence matching `weekday` generated by the weekly recurrence starting at `start_date`.
**Notes**:
- This function delegates date computation to `dateutil.rrule`; `start_date` is passed directly as `dtstart` without additional validation or conversion.

## Function: is_timestamp

```python
def is_timestamp(value: Any) -> bool
```

**is_timestamp**: Determine whether a value can be interpreted as a numeric timestamp.
**Signature**: def is_timestamp(value: Any) -> bool
**Parameters**:
- value (Any): Value to test for timestamp-likeness.
**Behavior**:
- If `value` is an instance of `bool`, return `False` (booleans are explicitly excluded even though they are subclasses of `int`).
- If `value` is not an instance of `int`, `float`, or `str`, return `False`.
- Otherwise, attempt to convert `value` to `float`:
- If `float(value)` succeeds, return `True`.
- If `float(value)` raises `ValueError`, return `False`.
**Returns**:
- `True` if `value` is not a boolean, is of type `int`, `float`, or `str`, and can be converted to `float` without raising `ValueError`; otherwise `False`.
**Notes**:
- Only `ValueError` from `float(value)` is handled; other exceptions (if any) are not caught by this function.

## Function: validate_ordinal

```python
def validate_ordinal(value: Any) -> None
```

**validate_ordinal**: Validate that a value is an integer Gregorian ordinal within configured bounds, raising an exception otherwise.
**Signature**: def validate_ordinal(value: Any) -> None
**Parameters**:
- value (Any): Candidate ordinal to validate.
**Behavior**:
- Type validation:
- If `value` is an instance of `bool` OR `value` is not an instance of `int`, raise `TypeError` with the message formatted as: "Ordinal must be an integer (got type <type>)." where `<type>` is `type(value)`.
- Range validation:
- If `value` is not within the inclusive range `[MIN_ORDINAL, MAX_ORDINAL]`, raise `ValueError` with the message formatted as: "Ordinal <value> is out of range.".
- If both checks pass, return normally without producing a value.
**Notes**:
- The bounds are taken from module-level constants `MIN_ORDINAL` and `MAX_ORDINAL`.

## Function: normalize_timestamp

```python
def normalize_timestamp(timestamp: float) -> float
```

**normalize_timestamp**: Convert a Unix epoch timestamp that may be expressed in seconds, milliseconds, or microseconds into seconds by inferring the unit solely from numeric magnitude against project-defined maximum thresholds (with inclusive upper bounds); reject values too large to be representable even as microseconds within the project’s supported domain.

**Signature**:
- def normalize_timestamp(timestamp: float) -> float

**Parameters**:
- timestamp (float): Unix epoch timestamp representing time since 1970-01-01 00:00:00 UTC, but possibly encoded in seconds, milliseconds, or microseconds. The unit is inferred only by comparing the numeric value to module-level maximum thresholds defined for this project (no metadata and no heuristic “guessing” beyond these comparisons).

**Behavior**:
- This function relies on three module-level constants that MUST be defined by the module and MUST reflect this project’s intended supported time domain:
  - `MAX_TIMESTAMP`: the maximum supported Unix epoch timestamp expressed in seconds.
  - `MAX_TIMESTAMP_MS`: the same maximum supported instant expressed in milliseconds.
  - `MAX_TIMESTAMP_US`: the same maximum supported instant expressed in microseconds.
- Critical project contract (authoritative cutoff; prevents unit misclassification):
  - The module MUST specify one explicit “latest supported instant” for the project’s domain, and `MAX_TIMESTAMP` MUST be the Unix-epoch seconds value of that instant.
  - The “latest supported instant” MUST be specified concretely in the module contract in exactly one of these authoritative forms:
    - an explicit numeric upper bound in Unix-epoch seconds (a concrete `MAX_TIMESTAMP` value), or
    - an explicit UTC datetime cutoff instant (year-month-day hour:minute:second in UTC) from which `MAX_TIMESTAMP` is derived by Unix-epoch conversion.
  - The cutoff MUST be a deliberate project boundary and MUST reflect what the project considers valid “seconds-valued” epoch timestamps.
  - The cutoff MUST NOT be inferred from unrelated maxima such as `datetime.datetime.max`, `datetime.date.max.toordinal()`, platform-dependent datetime limits, or any other “max datetime” mechanism unless that exact maximum is explicitly the project’s intended cutoff.
  - The module contract MUST include an explicit magnitude/domain statement describing the intended order-of-growth for valid seconds in this project, and this statement MUST be consistent with the chosen cutoff.
    - In particular, the project’s “valid seconds” domain MUST include large epoch-second magnitudes that can be comparable to (or larger than) the epoch-second value of far-future dates; therefore `MAX_TIMESTAMP` MUST be chosen accordingly so that such large-but-valid seconds are not misclassified as milliseconds.
    - Practically: `MAX_TIMESTAMP` MUST be set so that any value the project considers a valid seconds timestamp satisfies `timestamp <= MAX_TIMESTAMP` and therefore is returned unchanged (not divided by 1000).
- Invariants the constants MUST satisfy (by construction):
  - All three constants represent the same conceptual “latest supported instant” expressed at different resolutions.
  - `MAX_TIMESTAMP_MS == MAX_TIMESTAMP * 1000`
  - `MAX_TIMESTAMP_US == MAX_TIMESTAMP * 1_000_000`
  - Ordering MUST hold:
    - `MAX_TIMESTAMP < MAX_TIMESTAMP_MS < MAX_TIMESTAMP_US`
- Additional threshold-selection requirements (to preserve correct unit inference by magnitude):
  - The constants MUST be chosen so that within the supported domain (i.e., for all instants `t` such that `0 <= t <= MAX_TIMESTAMP` when expressed in seconds), the numeric magnitudes are cleanly separated:
    - the millisecond representation `t * 1000` is strictly greater than `MAX_TIMESTAMP` (so milliseconds cannot be mistaken for seconds), and
    - the microsecond representation `t * 1_000_000` is strictly greater than `MAX_TIMESTAMP_MS` (so microseconds cannot be mistaken for milliseconds).
  - Equivalently, the supported domain MUST satisfy strict magnitude separation such that:
    - every valid seconds-valued input `s` in-range satisfies `s <= MAX_TIMESTAMP`,
    - every valid milliseconds-valued input `ms` in-range satisfies `MAX_TIMESTAMP < ms <= MAX_TIMESTAMP_MS`,
    - every valid microseconds-valued input `us` in-range satisfies `MAX_TIMESTAMP_MS < us <= MAX_TIMESTAMP_US`.
  - This separation requirement is part of the module contract: it prevents large-but-valid seconds values (within the project’s intended domain) from being reinterpreted as milliseconds, and prevents milliseconds from being reinterpreted as microseconds.
- Unit selection and conversion are based solely on magnitude with inclusive upper bounds (implement comparisons exactly, and do not add additional heuristics):
  - If `timestamp <= MAX_TIMESTAMP`:
    - Treat `timestamp` as seconds and return it unchanged.
  - Else if `MAX_TIMESTAMP < timestamp <= MAX_TIMESTAMP_MS`:
    - Treat `timestamp` as milliseconds and return `timestamp / 1000`.
  - Else if `MAX_TIMESTAMP_MS < timestamp <= MAX_TIMESTAMP_US`:
    - Treat `timestamp` as microseconds and return `timestamp / 1_000_000`.
  - Else (i.e., `timestamp > MAX_TIMESTAMP_US`):
    - Raise `ValueError` with the message exactly: `The specified timestamp <repr> is too large.` where `<repr>` is `repr(timestamp)`.
- Boundary rules (must be implemented exactly as stated):
  - Inputs equal to a maximum are accepted and interpreted in that unit’s branch due to inclusive `<=` comparisons.
  - Inputs strictly greater than one maximum but less than or equal to the next maximum are interpreted as the higher-resolution unit (seconds → milliseconds → microseconds).
  - In particular:
    - `timestamp == MAX_TIMESTAMP` MUST be classified as seconds (no scaling),
    - only values strictly greater than `MAX_TIMESTAMP` may be eligible for millisecond interpretation,
    - only values strictly greater than `MAX_TIMESTAMP_MS` may be eligible for microsecond interpretation.
- Numeric behavior:
  - The function performs no rounding beyond standard floating-point division; it returns the computed `float` value in seconds.
- Side effects:
  - None. The function only computes and returns a value or raises an error.

**Returns**:
- A `float` Unix epoch timestamp in seconds:
  - Unchanged when `timestamp <= MAX_TIMESTAMP`.
  - Converted from milliseconds to seconds when `MAX_TIMESTAMP < timestamp <= MAX_TIMESTAMP_MS`.
  - Converted from microseconds to seconds when `MAX_TIMESTAMP_MS < timestamp <= MAX_TIMESTAMP_US`.
  - If `timestamp > MAX_TIMESTAMP_US`, the function does not return and instead raises `ValueError` as specified.

## Function: iso_to_gregorian

```python
def iso_to_gregorian(iso_year: int, iso_week: int, iso_day: int) -> datetime.date
```

**iso_to_gregorian**: Convert an ISO week-date (ISO year, week number, weekday) into the corresponding Gregorian calendar date.
**Signature**: def iso_to_gregorian(iso_year: int, iso_week: int, iso_day: int) -> datetime.date
**Parameters**:
- iso_year (int): ISO week-numbering year used to compute the date.
- iso_week (int): ISO week number; must be between 1 and 53 inclusive.
- iso_day (int): ISO weekday number; must be between 1 and 7 inclusive, where 1=Monday and 7=Sunday.
**Behavior**:
- Validate `iso_week`:
- If `iso_week` is not in the inclusive range 1..53, raise `ValueError` with the message "ISO Calendar week value must be between 1-53.".
- Validate `iso_day`:
- If `iso_day` is not in the inclusive range 1..7, raise `ValueError` with the message "ISO Calendar day value must be between 1-7".
- Compute the Gregorian date using the ISO definition that week 1 is the week containing January 4:
- Create `fourth_jan` as `datetime.date(iso_year, 1, 4)`.
- Compute `delta` as `datetime.timedelta(fourth_jan.isoweekday() - 1)`.
- Compute `year_start` as `fourth_jan - delta` (this yields the Monday starting ISO week 1).
- Compute `gregorian` as `year_start + datetime.timedelta(days=iso_day - 1, weeks=iso_week - 1)`.
- Return `gregorian`.
**Returns**:
- A `datetime.date` corresponding to the provided ISO week-date.
**Notes**:
- The computation relies on `date.isoweekday()` where Monday=1..Sunday=7.

**validate_bounds**: Validate that an interval bounds specifier is one of four allowed two-character forms.
**Signature**: def validate_bounds(bounds: str) -> None
**Parameters**:
- bounds (str): Bounds specifier string; must be exactly one of "()", "(]", "[)", or "[]".
**Behavior**:
- If `bounds` is not equal to any of the four allowed strings ("()", "(]", "[)", "[]"), raise `ValueError` with the message "Invalid bounds. Please select between '()', '(]', '[)', or '[]'.".
- If `bounds` is one of the allowed values, return normally.
**Notes**:
- No normalization (e.g., trimming whitespace) is performed; the comparison is exact.
